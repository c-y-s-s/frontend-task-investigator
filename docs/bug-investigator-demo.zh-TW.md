# Bug Investigator 面試 Demo

## 一句話定位

把散落的 Error、Console、Network 與 GitHub 程式碼整理成「排序後的可能原因」，再告訴工程師下一個成本最低的驗證動作；它不會在證據不足時假裝找到根因。

## 3–5 分鐘流程

1. 開啟 `http://localhost:3000/bug-investigator`，保留預設的付款 503 案例與 Replay。
2. 說明輸入包含實際行為、預期行為、Console 和 Network Response。
3. 執行調查，展示 6 個步驟：整理錯誤、搜尋程式碼、讀取檔案、搜尋 PR、產生假設、人工核准。
4. 指出第一名假設不是根因宣告；它同時引用輸入訊號與 `usePayment.ts`。
5. 展示驗證動作及 expected signal：先寫一個會重現 503 的測試，確認是否真的只有一次呼叫。
6. 說明停止條件：證據不符合才換下一個假設，不直接修改正式程式碼。
7. 核准「調查方向」，而不是核准一個未驗證的修復。

## 面試說法

> 一般聊天模型很容易看到錯誤就直接建議改 code。這個 Agent 先限制自己只能讀取證據，最多列三個假設，並為每個假設安排可觀察的驗證訊號。Human checkpoint 核准的是調查方向，不是讓 AI 自動修復。

## 完成邊界

面試版不接 Sentry、不控制瀏覽器、不執行 Console 指令、不讀正式環境 Log，也不建立修復 PR。這些都會擴大權限、安全與測試範圍，但不會讓核心 Agent 故事更清楚。
